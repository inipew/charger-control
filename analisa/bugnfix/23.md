# 23 — Configuration Semantics

## 1. Scope

Dokumen ini memperjelas perbedaan syntax, schema, semantic validity, normalization, dan runtime application.

## 2. Pipeline

```text
bytes
 → TOML parse
 → schema/version
 → semantic validation
 → normalization
 → EffectiveConfig
 → runtime swap
```

Setiap layer memiliki error berbeda agar diagnosis tidak kabur.

## 3. Defaults

Default hanya boleh diterapkan pada field/file yang memang missing dan telah didefinisikan kontraknya. Jangan menggunakan default sebagai recovery dari corruption.

```text
missing field → default
malformed field → error
invalid range → error
unknown version → migration/reject
```

## 4. Normalize

Normalization boleh menyederhanakan equivalent input, misalnya canonical duration/unit, tetapi tidak boleh mengubah unsafe value menjadi aman secara diam-diam.

Jika `resume_limit >= charge_limit`, itu validation error, bukan alasan untuk otomatis swap nilai.

## 5. Runtime immutability

Satu evaluation harus memakai satu `EffectiveConfig`. Reload menghasilkan object baru dan swap atomic setelah valid.

## 6. Reload

```text
active config A
 ↓
load B
 ↓
validate + normalize B
 ├─ fail → keep A
 └─ success → atomically activate B
```

Perubahan safety-relevant dapat memicu immediate reconciliation melalui runtime.

## 7. Versioning

Schema harus memiliki `config_version`. Migration harus:

```text
old supported
 → deterministic migration
 → validate
 → write new format atomically
```

Unknown version tidak boleh ditebak.

## 8. Testing

```text
[ ] missing file
[ ] missing field/default
[ ] malformed TOML
[ ] invalid range
[ ] cross-field conflict
[ ] old version migration
[ ] unknown version
[ ] reload failure retains active
[ ] reload success atomic
[ ] concurrent reload
```

## 9. Acceptance criteria

1. Default semantics eksplisit.
2. Invalid tidak menjadi default.
3. Reload atomic.
4. Version migration deterministic.
5. EffectiveConfig immutable per evaluation.
6. Safety-relevant reload menghasilkan reconciliation yang terkontrol.
