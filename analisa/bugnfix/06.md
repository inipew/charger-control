# 06 — Ownership & Crash Recovery

## 1. Tujuan

Ownership adalah evidence bahwa daemon sedang/sempat memiliki hak logical untuk mengendalikan charging. Sysfs tidak menyediakan lock yang cukup untuk masalah ini; actor lain tetap dapat menulis node.

## 2. Masalah snapshot-only

Flow sederhana:

```text
save ownership
 → write hardware
 → verify
 → clear ownership
```

masih ambigu jika crash di tengah. Startup hanya melihat file tetapi tidak mengetahui phase operation.

## 3. Target journal state

Gunakan state yang membedakan phase:

```text
Prepared
Applying
Verifying
Committed
RestorePending
Failed
```

Dengan:

```text
operation_id
intent_generation
original_state
requested_target
node results
last error
created_at/monotonic metadata
schema_version
checksum
```

Wall clock hanya metadata; recovery timing menggunakan monotonic runtime setelah startup.

## 4. Crash matrix

### Crash sebelum persistence
Tidak ada mutation boleh terjadi sebelum evidence durable. Recovery tidak perlu menebak operation yang belum dimulai.

### Crash setelah persistence sebelum write
Startup melihat `Prepared`; operation dapat dibatalkan/reconciled berdasarkan actual state.

### Crash setelah sebagian write
Startup melihat `Applying`; wajib read actual node dan menentukan apakah target sudah tercapai, mixed, atau unknown.

### Crash setelah write sebelum verify
State `Verifying`/`Applying` harus menyebabkan readback, bukan asumsi sukses.

### Crash setelah verify sebelum commit
Recovery boleh mengulang read/verify. Jangan langsung melakukan opposite mutation hanya karena commit belum tertulis.

## 5. Atomic persistence

Jangan overwrite langsung:

```text
open ownership.state
write partial
crash
→ corrupt file
```

Gunakan:

```text
serialize
 → write temp in same directory
 → fsync temp
 → rename atomically
 → fsync directory jika durability diperlukan
```

File dan directory harus permission-restricted dan symlink attack-resistant.

## 6. Recovery algorithm

```text
startup
 ↓
load journal
 ↓
validate schema/checksum
 ↓
no journal → clean
 ↓
unfinished journal
 ↓
read actual hardware
 ↓
compare requested/original/actual
 ├─ already safe/verified → finalize
 ├─ target partially applied → reconcile
 ├─ unknown → protective path
 └─ evidence corrupt → fail closed
```

Recovery tidak boleh langsung memilih `set_charging(true)` sebagai default.

## 7. Original state

Jika controller perlu restore state awal, state tersebut harus disimpan sebelum mutation dan memiliki semantics yang jelas:

```text
original_control_state
original_observed_electrical_state
```

Jangan mencampur original physical state dengan desired policy state.

## 8. Release ownership

Release bukan:

```text
clear file
```

Release adalah transaction:

```text
restore/relinquish decision
 → apply if required
 → readback
 → verify
 → persist release committed
 → clear/archive evidence
```

Jika restore gagal, ownership evidence harus tetap ada agar recovery dapat mencoba lagi.

## 9. Shutdown

Shutdown harus menggunakan controller/runtime yang sama. IPC tidak boleh langsung mengubah hardware lalu exit.

Semantics produk harus eksplisit:

```text
shutdown → restore previous state
```

atau:

```text
shutdown → relinquish / leave untouched
```

Jangan mencampur keduanya di worker yang berbeda.

## 10. Stale ownership

Stale berarti process mati tanpa clear journal, bukan otomatis corruption.

Startup harus membedakan:

```text
valid unfinished operation
corrupt journal
unknown schema
```

Valid stale operation dapat direcover. Corrupt state membutuhkan conservative recovery.

## 11. Multiple daemon instances

Ownership file bukan singleton lock. Gunakan process/file lock terpisah untuk memastikan hanya satu controller aktif.

Jika dua daemon hidup bersamaan, kedua-duanya dapat menulis sysfs walaupun ownership state valid.

## 12. External actor

Setelah ownership acquired, vendor HAL/thermal service/root CLI dapat mengubah state. Ownership berarti logical responsibility, bukan physical exclusivity.

Controller harus mendeteksi external modification lewat reconciliation.

## 13. Testing

Crash injection pada:

```text
[ ] before journal write
[ ] after journal fsync
[ ] after first node
[ ] after middle node
[ ] after final node
[ ] before readback
[ ] after readback
[ ] before verify commit
[ ] after verify
[ ] before release clear
```

Corruption tests:

```text
[ ] empty file
[ ] truncated file
[ ] invalid TOML/format
[ ] wrong checksum
[ ] unknown schema version
[ ] malicious path/value
```

## 14. Acceptance criteria

1. Tidak ada hardware mutation tanpa durable evidence.
2. Crash di setiap phase dapat direcover secara deterministic.
3. Partial write selalu dibaca ulang.
4. Release hanya committed setelah proof yang diperlukan.
5. Corrupt journal tidak dianggap clean.
6. Ownership tidak menjadi alasan untuk infinite write fight.
7. Shutdown mempunyai satu semantics dan satu execution path.
