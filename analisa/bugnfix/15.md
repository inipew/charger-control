# 15 — Desired, Applied, Actual & Verified State

## 1. Masalah inti

Charging controller tidak boleh memakai satu boolean `enabled` untuk mewakili seluruh kenyataan. Empat layer memiliki lifecycle berbeda.

```text
Policy
  ↓
DESIRED
  ↓
APPLY operation
  ↓
APPLIED
  ↓
READBACK
  ↓
ACTUAL
  ↓
verification rules
  ↓
VERIFIED
```

## 2. Definitions

### Desired
State yang diperintahkan policy/controller sekarang.

### Applied
Write operation telah diterima oleh hardware interface untuk operation tertentu. Ini bukan proof physical state.

### Actual
State yang dibaca kembali dari kernel/vendor nodes.

### Verified
Actual memenuhi acceptance criteria profile untuk desired pada waktu tertentu.

## 3. Example false success

```text
Desired = ChargingDisabled
write(false) = Ok
Applied = Disabled
readback = Enabled
```

Kesalahan fatal adalah langsung mengembalikan `Synced` setelah `write(false)=Ok`.

Yang benar:

```text
Applied
 → readback
 → Actual=Enabled
 → Verified=false
 → reconciliation
```

## 4. Controller record

Operation state minimal menyimpan:

```text
intent_generation
operation_id
desired target
start timestamp
per-node write results
actual readback
verification result
verification timestamp
retry metadata
last error
```

## 5. Reconciliation algorithm

```text
fresh snapshot/readback
 ↓
policy → desired
 ↓
read actual
 ↓
actual == desired?
 ├─ yes → verify/commit
 └─ no  → apply
             ↓
          readback
             ↓
          verify
```

Jika actual sudah verified sesuai desired, jangan melakukan redundant write.

## 6. External mutation

Contoh:

```text
desired OFF
verified OFF
        ↓
vendor actor → ON
        ↓
actual ON
        ↓
verification invalidated
        ↓
reconcile
```

Previous verified state harus dianggap stale ketika evidence berubah.

## 7. Generation race

```text
intent #10 = OFF
operation A
intent #11 = ON
operation B
late A result
```

Result A tidak boleh meng-commit state untuk intent #11. Karena itu operation identity dan intent generation harus berbeda.

## 8. Verification evidence

Verified state harus memiliki provenance:

```text
operation_id
read timestamp/age
source nodes
evidence values
profile version
```

Tanpa evidence, status UI/API hanya boleh menyebut `Applied` atau `Unknown`, bukan `Verified`.

## 9. Unmanaged

`Unmanaged` bukan state hardware actual. Ia adalah controller intent:

```text
Desired = Unmanaged
 → controller relinquishes
 → no charging write
```

Actual hardware state tetap boleh ON/OFF dan harus dilaporkan sebagai physical evidence terpisah.

## 10. Retry

Retry dilakukan bila desired masih sama dan operation belum verified. Jika desired berubah, retry lama dibatalkan berdasarkan generation.

## 11. Testing

```text
[ ] write success/readback success
[ ] write success/readback wrong
[ ] delayed readback
[ ] unknown readback
[ ] external mutation
[ ] desired changes mid-operation
[ ] no redundant verified write
[ ] Unmanaged produces zero writes
```

## 12. Acceptance criteria

1. API tidak false-report synced.
2. Four-layer state dapat diobservasi.
3. Verified selalu memiliki evidence.
4. External mutation invalidates verification.
5. Late operation result tidak dapat overwrite intent baru.
6. Unmanaged tidak dianggap sebagai physical OFF/ON.
