# 15 — Desired vs Applied vs Actual State

## Masalah
`target`, hasil write, dan kondisi hardware adalah tiga fakta berbeda. Menyatukannya menyebabkan false success dan sulit menangani external actor.

## Invariant
- **I-STATE-001**: desired state adalah keputusan policy, bukan bukti hardware.
- **I-STATE-002**: applied state adalah hasil operasi controller, bukan bukti readback.
- **I-STATE-003**: actual state berasal dari hardware readback.
- **I-STATE-004**: verified state hanya boleh `Verified` setelah evidence memenuhi requirement.

## State model
```text
DesiredState
    |
    v
ApplyResult
    |
    v
ActualState <---- external actor / kernel
    |
    v
VerificationState
```

Controller sebaiknya menyimpan:
- desired intent + generation;
- last operation ID;
- applied result;
- actual readback;
- verification result;
- timestamp/age;
- failure/retry metadata.

## Reconciliation
Loop normal:
1. snapshot hardware;
2. DecisionEngine menghasilkan desired state;
3. compare desired vs actual;
4. apply hanya bila perlu;
5. readback;
6. verify;
7. bila mismatch, classify external change/error dan jadwalkan reconciliation.

Jangan melakukan write pada setiap polling jika actual sudah sesuai.

## External mutation
Jika vendor daemon mengubah node setelah daemon kita berhasil apply, desired tetap dapat sama sementara actual berubah. Controller harus mendeteksi mismatch dan menerapkan arbitration policy, bukan menganggap operasi lama masih valid.

## Acceptance criteria
1. Status API dapat membedakan desired/applied/actual/verified.
2. Test memodelkan external mutation setelah successful apply.
3. Tidak ada `set_*()` yang mengembalikan success tanpa readback ketika capability mengharuskan verification.
4. Retry tidak mengulang write yang sudah verified.
