# 13 — Power Supply & Kernel Semantics

## 1. Scope

Linux `power_supply` adalah compatibility boundary. Property availability dan semantics bukan kontrak universal Android vendor. Policy hanya boleh menerima normalized evidence dari reader/profile.

## 2. Pipeline

```text
/sys/class/power_supply/*
        ↓
raw bytes
        ↓
parse
        ↓
property semantic
        ↓
unit/sign normalization
        ↓
freshness/provenance
        ↓
SensorSnapshot
```

## 3. Availability states

Setiap property sebaiknya dapat diklasifikasikan:

```text
Absent
Unreadable
Malformed
InvalidRange
Valid
Stale
```

`Absent` tidak sama dengan `Unreadable`, dan keduanya tidak otomatis berarti zero.

## 4. Presence semantics

Jangan menyimpulkan charger presence dari satu field secara universal:

```text
ONLINE=0
STATUS=NotCharging
CURRENT=0
```

merupakan tiga evidence berbeda.

Profile menentukan property authoritative untuk presence. Domain representation:

```text
Some(true)  = known online
Some(false) = known offline
None        = unknown
```

## 5. Status vs current

`STATUS=Charging` adalah reported control/charging status. Current adalah electrical measurement yang dipengaruhi load, sign convention, measurement lag, dan driver.

Karena itu:

```text
status = charging
current = 50mA
```

tidak otomatis contradiction. Verification harus mengetahui evidence role setiap property.

## 6. Unit conversion

Domain units harus explicit:

```text
capacity → percent
current → mA
voltage → mV jika diperlukan
temperature → deci-Celsius
```

Conversion dilakukan sekali di reader/profile dan checked.

## 7. Sign convention

Profile harus mendokumentasikan apakah positive current berarti battery charging atau discharging. Jangan hard-code asumsi global.

Tambahkan tests untuk:

```text
positive
zero
negative
large
overflow
```

## 8. Staleness

Snapshot timestamp adalah capture time, bukan waktu terakhir file descriptor dibuka. Cache harus memiliki TTL/age policy.

Setelah suspend lama, cached sensor tidak boleh langsung dipakai sebagai proof.

## 9. Property-specific fallback

Fallback hanya boleh digunakan jika semantics memang terdefinisi. Contoh:

```text
optional property absent → capability unavailable
required property absent → profile unsupported/degraded
read error → evidence unavailable
malformed → invalid evidence
```

Jangan:

```text
read error → 0
```

## 10. Kernel/vendor mutation

Kernel driver dapat memperbarui values asynchronously. Reader harus menerima eventual consistency dan verification delay; tidak boleh menganggap read setelah write selalu synchronous.

## 11. Testing fixtures

Setiap profile harus menyimpan raw fixture dan expected normalized result:

```text
raw status
raw current
raw temp
raw capacity
raw online
→ expected snapshot
```

Test fixture juga harus mencakup missing/malformed values.

## 12. Acceptance criteria

1. Tidak ada universal heuristic untuk presence.
2. Unit/sign terdokumentasi per property/profile.
3. Invalid tidak menjadi zero.
4. Cache memiliki freshness semantics.
5. Snapshot menyimpan evidence yang dapat ditelusuri.
6. Verification tidak menyamakan status dengan electrical current.
7. Setiap supported profile memiliki raw fixture.
