# 14 — Hardware Capability & Vendor Profile

## Tujuan
Memisahkan kemampuan hardware dari policy charging. Device/vendor berbeda dapat memiliki node control berbeda, sehingga generic implementation harus berbasis capability/profile.

## Invariant
- **I-CAP-001**: profile mendeskripsikan hardware, bukan business policy.
- **I-CAP-002**: setiap control node memiliki kind, priority, required/optional, readback support, dan write semantics.
- **I-CAP-003**: capability discovery tidak boleh diam-diam mengubah policy.
- **I-CAP-004**: daemon tidak mengambil ownership sebelum capability minimum tervalidasi.

## Model profile
```text
DeviceProfile
  identity: manufacturer/model/soc/kernel
  controls:
    - path
      kind
      enable_value
      disable_value
      readable
      writable
      required
      priority
      quirks
  sensors: ...
  current_sign: ...
  timing: ...
```

Gunakan priority untuk beberapa node yang merepresentasikan capability sama. Hindari hard-code daftar path tersebar di banyak module.

## Capability lifecycle
```text
Discover -> Validate -> Select -> Acquire ownership -> Operate -> Verify -> Release
```

Jika required capability hilang, daemon masuk safe state dan tidak melakukan write spekulatif.

## Vendor quirks
Quirk harus eksplisit, teruji, dan terikat profile. Contoh yang layak dimodelkan: write membutuhkan delay, readback terlambat, nilai enable berbeda, node tersedia hanya setelah boot, atau current sign terbalik.

Jangan membuat daftar device detection yang besar tanpa test. Generic profile menjadi fallback hanya bila capability benar-benar kompatibel.

## Acceptance criteria
1. Tidak ada daftar sysfs control penting yang diduplikasi di policy/controller/CLI.
2. Device yang capability-nya tidak cukup tidak dianggap berhasil hanya karena write tidak error.
3. Profile test mencakup supported, partially supported, dan incompatible device.
4. Penambahan vendor profile tidak mengubah DecisionEngine.
