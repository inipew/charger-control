# 14 — Hardware Capability & Vendor Profile

## Tujuan
Membuat satu binary dapat menangani variasi Android tanpa hard-coded assumptions yang berbahaya.

## Profile bukan policy
Profile hanya menjelaskan:
```text
node paths
node kind
value semantics
unit/sign
required/optional
priority
authoritative capability
quirks
```
Policy tetap berada di DecisionEngine.

## Capability discovery
Startup:
```text
candidate profile
 → open nodes
 → read/validate
 → probe capability
 → build effective capabilities
```
Declaration profile tanpa probing tidak cukup untuk claim supported.

## Node metadata
```rust
struct ControlNode {
    path: PathBuf,
    kind: NodeKind,
    required: bool,
    priority: u8,
    authoritative: bool,
}
```

## Generic vs vendor profile
```text
known device/profile → tested semantics
unknown device → generic conservative profile
unsupported capability → do not write
```
Jangan memakai device-family saja sebagai bukti capability.

## Quirk handling
Vendor-specific sign/value inversion harus menjadi data profile, bukan `if vendor == ...` yang tersebar di controller/reader.

## Compatibility evidence
Profile harus memiliki fixture raw sysfs dan test expected semantic state.

## Acceptance criteria
1. Required/optional explicit.
2. Priority explicit.
3. Capability hasil probe dapat ditampilkan pada status.
4. Generic profile tidak melakukan speculative write.
5. Setiap vendor quirk memiliki test fixture.
