# 14 — Hardware Capability & Vendor Profile

## 1. Tujuan

Satu binary harus dapat berjalan pada Android vendor berbeda tanpa menyebarkan hard-coded path/value assumptions ke seluruh codebase.

## 2. Profile versus policy

Profile menjawab:

```text
Hardware ini menyediakan apa?
Bagaimana membaca property?
Bagaimana menulis control node?
Apa unit/sign/value semantics-nya?
```

Policy menjawab:

```text
Kapan charging harus ON/OFF?
```

Jangan menaruh `charge_limit` atau thermal policy di vendor profile.

## 3. Capability discovery

Startup flow:

```text
device identity/evidence
 ↓
candidate profile
 ↓
probe paths
 ↓
validate readable/writable semantics
 ↓
build EffectiveCapabilities
 ↓
controller/runtime
```

Deklarasi path di profile saja tidak cukup untuk claim supported.

## 4. Node metadata

```rust
struct ControlNode {
    path: PathBuf,
    kind: NodeKind,
    required: bool,
    priority: u8,
    authoritative: bool,
    enable_value: String,
    disable_value: String,
}
```

Tambahkan semantics retryable errors dan verification role bila diperlukan.

## 5. Required versus optional

```text
required missing
 → unsupported/degraded

optional missing
 → continue without that capability
```

Controller tidak boleh speculative-write node yang tidak terbukti ada/valid.

## 6. Generic profile

Unknown device:

```text
detect known safe capability
 → use only proven nodes
```

Jangan menebak path berdasarkan SoC/device-family saja.

Jika capability tidak terbukti, `Unmanaged`/degraded lebih aman daripada write yang salah.

## 7. Quirk handling

Contoh quirk:

```text
vendor A: positive current = charging
vendor B: negative current = charging
vendor C: control value = 255/0
```

Representasikan sebagai profile data/strategy, bukan:

```rust
if vendor == "X" { ... }
```

yang tersebar di controller dan reader.

## 8. Profile selection

Identity dapat menjadi hint, tetapi capability probe adalah authority. Jika identity mengatakan profile A tetapi node semantics tidak cocok, profile harus ditolak atau masuk degraded mode.

## 9. Profile versioning

Profile schema harus memiliki version. Perubahan semantics harus menghasilkan fixture/test baru, bukan silent behaviour change.

## 10. Evidence package

Untuk setiap supported profile simpan:

```text
device/SoC/kernel/Android version
raw node listing
raw sample values
normalized expectation
control write values
verification evidence
boot/suspend/reboot observations
```

## 11. Safety constraints

Profile tidak boleh membuka arbitrary path dari config/IPC. Path harus berasal dari trusted compiled/profile data atau validated package.

## 12. Testing

```text
[ ] profile match
[ ] profile mismatch
[ ] required node missing
[ ] optional node missing
[ ] permission denied
[ ] malformed value
[ ] wrong unit/sign
[ ] quirk mapping
[ ] unknown device
[ ] capability changes after boot
```

## 13. Acceptance criteria

1. Profile tidak berisi policy global.
2. Capability hasil probe dapat diobservasi.
3. Required/optional jelas.
4. Unknown hardware tidak speculative-write.
5. Vendor quirks terisolasi dan teruji.
6. Supported claim memiliki real-device evidence.
