# 11 — ANDROID / VENDOR / MAGISK DEPLOYMENT SPECIFICATION

## Tujuan

Memastikan design core tetap benar saat berjalan pada Android nyata dengan vendor kernel, power HAL, thermal daemon, SELinux, Magisk lifecycle, dan power_supply nodes yang berbeda.

## Vendor variability

Jangan mengasumsikan path universal.

Contoh kategori:

```text
battery
usb
ac
dc
wireless
bms
main
parallel
```

Profile menentukan node yang dipercaya dan semantics-nya.

## Hardware profile

Profile mendeskripsikan:

```text
profile name
charging nodes
optional suspend nodes
battery nodes
online nodes + priority
current unit/sign
required/optional nodes
verification strategy
capabilities
```

Profile bukan tempat business policy.

## Capability detection

Distinguish:

```text
node missing
node unreadable
node read-only
feature unsupported
feature supported but currently unavailable
```

Jangan menyamakan semuanya sebagai `false`.

## External actors

Daemon dapat berkompetisi dengan:

```text
vendor charger service
power HAL
thermal service
kernel driver
Magisk module/script
user/manual sysfs write
```

Actual state harus selalu diverifikasi dan reconciliation harus mampu menangani external modification.

## Startup

```text
Magisk service start
→ process lock
→ config
→ ownership recovery
→ hardware probe
→ reader
→ runtime
```

Jangan mengaktifkan policy sebelum recovery selesai.

## Suspend / resume

Android dapat melakukan suspend panjang. Setelah resume:

```text
invalidate stale snapshot
→ re-read sensors
→ re-read hardware
→ evaluate
```

Jangan memperlakukan elapsed wall-clock sleep sebagai continuous sensor history.

## Charger plug/unplug

Netlink event harus mempercepat detection, tetapi actual `online/status/current` harus dibaca kembali.

Gunakan debounce untuk noise dari vendor/kernel.

## SELinux dan permission

Release package harus mendokumentasikan kebutuhan:

```text
root
sysfs write permission
/data/adb access
socket ownership/group
SELinux compatibility
```

Jangan mengatasi permission failure dengan fallback yang diam-diam mengubah policy.

## Device profile testing

Setiap profile harus mempunyai:

```text
known nodes
expected values
control write semantics
verification semantics
current sign convention
thermal units
online semantics
```

Sebelum profile dianggap production-ready, lakukan test pada device/kernel yang menjadi target.

## Rollback

Update daemon/module harus memiliki rollback path. Jika binary baru gagal startup atau recovery ownership gagal, persistent ownership tidak boleh hilang.

## Upgrade compatibility

Perubahan schema/config/ownership format harus versioned. Upgrade daemon tidak boleh membuat ownership lama tidak dapat dibaca tanpa migration/recovery strategy.

## Acceptance

Release Android dianggap valid jika:

- boot recovery bekerja;
- charger plug/unplug stabil;
- thermal protection benar;
- limit/resume benar;
- external modification terdeteksi;
- suspend/resume tidak merusak state;
- crash recovery berhasil;
- permission/SELinux failure fail-safe;
- rollback tidak kehilangan ownership journal.
