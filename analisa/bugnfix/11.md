# 11 — Android / Vendor / Magisk

## 1. Platform reality

`charger-control` berjalan di lingkungan yang jauh lebih heterogeneous daripada Linux desktop. Nama node, topology `power_supply`, unit, sign current, charging control mechanism, SELinux policy, boot timing, dan actor vendor dapat berbeda antar perangkat.

Karena itu generic implementation harus conservative dan capability/profile-driven.

## 2. Boot sequence

Recommended:

```text
Magisk late-start service
 ↓
wait for required system readiness with bounded timeout
 ↓
single-instance lock
 ↓
validate runtime dirs/config
 ↓
load vendor profile/capabilities
 ↓
recover stale ownership
 ↓
fresh baseline snapshot
 ↓
policy evaluation
 ↓
steady-state loop
```

Jangan melakukan charging mutation hanya karena service script berhasil dieksekusi.

## 3. `service.sh`

Magisk startup script sebaiknya hanya bootstrap daemon dan tidak melakukan loop policy sendiri. Script harus non-blocking terhadap boot dan mempunyai process supervision yang jelas.

Anti-pattern:

```text
service.sh
 → infinite shell loop
 → direct sysfs writes
```

Target:

```text
service.sh
 → prepare environment
 → exec/spawn daemon
```

## 4. Singleton

Gunakan lock/process identity agar update/restart tidak menghasilkan dua daemon:

```text
old daemon alive
new daemon starts
        ↓
lock acquisition fails
        ↓
new daemon exits
```

Lock bukan ownership journal. Keduanya mempunyai fungsi berbeda.

## 5. Vendor actors

Assume actor berikut dapat menulis state:

```text
kernel charger driver
Android framework
vendor HAL/daemon
thermal service
battery manager
other root module
charger-control CLI
```

Logical ownership tidak mencegah mereka. Controller harus mendeteksi external mutation dan memiliki bounded convergence.

## 6. Capability/profile model

Profile sebaiknya mendeskripsikan:

```text
required control nodes
optional control nodes
authoritative read node
supporting evidence
unit/sign
status mapping
write values
verification strategy
retryable errors
boot availability
```

Profile adalah data/capability description, bukan tempat menaruh global policy seperti `charge_limit`.

## 7. SELinux

Dokumentasikan kebutuhan minimal:

```text
process domain
sysfs read/write labels
runtime directory
Unix socket
config file
log destination
```

Jika denial terjadi, jangan langsung membuat allow rule luas. Tentukan resource yang benar-benar diperlukan dan mengapa daemon membutuhkannya.

## 8. Delayed node availability

Pada boot, `/sys/class/power_supply` atau vendor control node dapat muncul terlambat.

Flow:

```text
profile known
node absent
 → capability temporarily unavailable
 → bounded probe/retry
```

Jangan menganggap absence permanen pada detik pertama boot.

## 9. Disable/update/uninstall

Lifecycle harus:

```text
request stop
 ↓
block new mutation
 ↓
controller finalization
 ↓
verify required final state
 ↓
persist recovery evidence if failed
 ↓
stop process
```

Jika module di-disable saat daemon mati, stale ownership tetap harus dapat dipulihkan oleh mekanisme startup/cleanup yang disepakati.

## 10. Reboot

Sebelum reboot, daemon mungkin tidak mendapat graceful shutdown. Karena itu ownership persistence harus menjadi safety net.

```text
running
 → abrupt reboot
 → journal survives
 → next boot recovery
 → read actual
 → reconcile
```

## 11. Device without capability

Jika required capability tidak ada:

```text
do not guess path
 do not write fallback node
 → degraded/unsupported
 → no unsafe charging control
```

Kernel tetap mengendalikan charging secara normal jika daemon relinquish control.

## 12. Acceptance test matrix

```text
[ ] cold boot
[ ] warm reboot
[ ] charger connected before boot
[ ] charger connected after boot
[ ] node appears late
[ ] daemon restart
[ ] Magisk disable
[ ] Magisk update
[ ] uninstall
[ ] SELinux enforcing
[ ] vendor actor interference
[ ] unsupported profile
```

## 13. Acceptance criteria

1. Startup tidak blocking boot.
2. Satu daemon instance.
3. Recovery berjalan sebelum policy mutation.
4. Device capability terdeteksi, bukan ditebak.
5. SELinux permission minimal.
6. Update/disable/reboot tidak meninggalkan uncontrolled mutation.
7. External actor menghasilkan bounded reconciliation.
