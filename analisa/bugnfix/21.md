# 21 — Error Taxonomy & Recovery Policy

## 1. Tujuan

Error bukan sekadar string. Jenis error harus menentukan apakah operation ditolak, di-retry, direkonsiliasi, atau masuk fault.

## 2. Canonical taxonomy

```text
ConfigParse
ConfigValidation
UnsupportedCapability
NodeAbsent
ReadError
WriteError
TransientIo
PermissionDenied
InvalidHardwareValue
VerificationFailed
ExternalModification
PersistenceError
ProtocolError
Timeout
InternalInvariantViolation
```

## 3. Recovery mapping

| Error | Recovery |
|---|---|
| Parse/validation | reject, no retry |
| Unsupported | degraded/Unmanaged |
| transient I/O | bounded retry |
| permission denied | deployment fault |
| invalid hardware value | fail safe |
| verification failed | reconcile + bounded retry |
| persistence error | do not claim committed |
| protocol error | reject request |
| timeout | classify operation state, never assume success |
| internal invariant | fail closed + diagnostics |

## 4. Unknown / Offline / Fault

```text
Unknown = evidence tidak tersedia
Offline = evidence source memang offline
Fault = safety/operation contract tidak dapat dipenuhi
```

Jangan mengubah `Unknown` menjadi `Offline` untuk mempermudah policy.

## 5. Retry rules

Retry harus:

```text
bounded
monotonic deadline
operation/generation aware
only for retryable classes
```

Failure counter reset setelah **verified success**, bukan hanya write success.

## 6. Error propagation

Preserve causal chain:

```text
Policy/Runtime
 → ControllerError
 → HardwareIoError
 → OS/vendor cause
```

API/UI menerima stable category/code, sementara log menyimpan sanitized cause.

## 7. Timeout

Timeout tidak berarti write gagal. Bisa jadi operation selesai tetapi acknowledgement hilang.

Setelah timeout:

```text
read actual
 → determine state
 → reconcile if necessary
```

## 8. Observability

Error event minimal:

```text
operation_id
intent_generation
category
node/capability identifier
attempt
retry_at
sanitized cause
```

## 9. Testing

```text
[ ] each error maps to expected recovery
[ ] transient retries
[ ] permanent errors stop retry
[ ] timeout readback
[ ] verification failure
[ ] persistence failure
[ ] unknown vs offline
[ ] internal invariant
```

## 10. Acceptance criteria

1. Tidak ada `unwrap` yang mengubah runtime error menjadi crash tanpa classification.
2. Setiap controller error punya recovery policy.
3. Timeout tidak false-success.
4. Unknown/offline/fault tetap berbeda.
5. Error dapat didiagnosis dari structured evidence.
