# 01 — Master Remediation Specification

## 1. Tujuan

Dokumen ini adalah master engineering specification untuk menjadikan `charger-control` sebuah daemon Android yang safety-critical secara praktis: keputusan deterministik, hardware mutation terpusat, ownership dapat dipulihkan setelah crash, configuration tidak silent-fallback, dan lifecycle Android/Magisk tidak meninggalkan charger pada state yang tidak dimaksudkan.

Dokumen ini **bukan sekadar daftar fitur**. Setiap temuan harus dapat ditelusuri dari behaviour saat ini → risiko → kontrak yang benar → implementasi → test yang membuktikan kontrak.

## 2. Baseline arsitektur saat ini

Workspace memisahkan `charger-core`, `charger-daemon`, `charger-ctl`, dan `test_os`. Core sudah mempunyai snapshot sensor, decision engine, hardware controller, verification, ownership persistence, scheduler, netlink monitor, fake clock, serta mock hardware. Fondasi ini sudah benar, tetapi beberapa boundary masih belum sepenuhnya enforceable.

Target flow:

```text
power_supply / kernel
        │
        ▼
 BatteryReader ──► SensorSnapshot
                         │
                         ▼
                   DecisionEngine
                         │
                         ▼
                  HardwareIntent
                         │
                         ▼
                 HardwareController
                    │          │
             Ownership       Verify
                    │          │
                    └────┬─────┘
                         ▼
                    HardwareIo
                         │
                         ▼
                       sysfs
```

Scheduler hanya menentukan **WHEN** evaluasi dijalankan. Policy menentukan **WHAT** yang seharusnya terjadi. Controller menentukan **HOW** hardware dikonvergensikan.

## 3. Temuan P0

### P0-01 — Shutdown IPC tidak boleh mematikan process dari worker

Jika IPC worker memanggil `process::exit()`, seluruh runtime dapat berhenti sebelum monitor/runtime menyelesaikan restore, verification, persistence, dan cleanup.

Flow yang berbahaya:

```text
IPC thread
  → Shutdown
  → process::exit()
  → monitor mati
  → shutdown_restore() mungkin belum berjalan
```

Flow yang benar:

```text
IPC/SIGTERM
  → ShutdownRequested
  → runtime menerima event
  → stop accepting new mutations
  → resolve ownership policy
  → restore/relinquish sesuai kontrak
  → verify
  → persist final state
  → close IPC
  → exit
```

Satu komponen harus menjadi owner lifecycle termination. IPC hanya producer event.

### P0-02 — `thermal_cutoff` harus menjadi master switch

`max_temp_dc` tidak boleh dengan sendirinya mengaktifkan thermal protection. Jika:

```toml
thermal_cutoff = false
max_temp_dc = 450
```

maka temperatur 500 dC tidak boleh menyebabkan `ThermalCutoff` dari policy userspace.

Namun kernel/vendor safety mechanism tetap boleh bekerja. Daemon hanya mengendalikan policy miliknya sendiri.

### P0-03 — Bypass/manual control tidak boleh direct sysfs

Semua mutation harus melewati `HardwareController`, termasuk command dari CLI/IPC. Kalau bypass langsung memanggil `set_charging()`, maka ownership, persistent evidence, verification, retry, dan audit trail dapat dilewati.

Kontrak:

```text
CLI/IPC
  → ManualIntent
  → Runtime
  → HardwareController
  → ownership
  → write
  → verify
```

Tidak boleh:

```text
IPC → control::set_charging()
```

### P0-04 — IPC socket `0666` terlalu permisif

Daemon root yang mengontrol charging tidak boleh menerima command privileged dari sembarang local process. Minimal gunakan mode `0660`, group khusus, directory permission ketat, dan authorization berdasarkan command.

Shutdown, bypass, reload, dan mutating commands harus dianggap privileged.

## 4. Temuan P1

### P1-01 — Config parse/validation error tidak boleh menjadi default

Bedakan:

```text
missing config     → boleh create default, jika kontrak memang begitu
I/O error          → FAIL
TOML parse error   → FAIL
validation error   → FAIL
```

Jangan melakukan:

```text
corrupt config
  → default
  → save default
  → config asli hilang
```

### P1-02 — Validation harus satu source of truth

CLI validation saja tidak cukup karena daemon dapat membaca TOML langsung. Buat:

```rust
impl Config {
    pub fn validate(&self) -> Result<(), ConfigError>;
    pub fn normalize(self) -> Result<EffectiveConfig, ConfigError>;
}
```

CLI dan daemon harus memanggil API yang sama.

### P1-03 — Hardware partial write harus direkonsiliasi

Misalnya target OFF membutuhkan node A dan B:

```text
A = OFF  ✓
B = write failed ✗
```

Jangan sekadar return error lalu menunggu scheduler. Controller harus membaca actual state dan menentukan apakah perlu retry, converge ke safe target, atau masuk fault.

### P1-04 — Ownership persistence harus recoverable

Snapshot `ownership.state` cukup untuk happy path tetapi lemah jika crash terjadi di antara:

```text
save ownership
set node A
set node B
verify
clear ownership
```

Target desain menggunakan phase/op-id sehingga startup dapat membedakan `Prepared`, `Applying`, `Verifying`, `Committed`, dan `RestorePending`.

### P1-05 — `Desired`, `Applied`, `Actual`, `Verified` harus dipisahkan

`set_charging(true)` sukses hanya berarti write API berhasil. Itu bukan bukti kernel actual state sudah ON.

```text
Desired    = keputusan policy
Applied    = write operation accepted
Actual     = state read dari hardware
Verified   = actual memenuhi acceptance criteria
```

## 5. Temuan P1/P2 tambahan

### Reader

- `Mixed/Unknown` tidak boleh dipetakan menjadi `NoChargingNodeFound`.
- Nilai raw `i64` harus dikonversi ke `i32` secara checked.
- Unit µA/µV/mA dan tanda current harus dinormalisasi di reader, bukan di policy.
- Generic hard-coded reader dan profile-driven reader jangan menduplikasi sumber kebenaran.

### Verification

`current_ma <= 100` sebaiknya secondary evidence, bukan satu-satunya definisi disabled. Status/control node, electrical current, dan online/presence harus diperlakukan sebagai evidence terpisah.

### Temporal

Semua deadline/backoff memakai monotonic `Instant`. Wall clock hanya untuk log/metadata.

### Scheduler

Netlink adalah accelerator, bukan correctness mechanism. Polling/reconciliation wajib tetap ada ketika event hilang.

## 6. Kontrak policy → hardware

Mapping canonical:

| Policy | Target | Mutation |
|---|---|---|
| Normal Charging | `ChargingEnabled` | enable + verify |
| Limit Reached | `ChargingDisabled` | disable + verify |
| Thermal Cutoff | `ChargingDisabled` | disable + verify |
| Fault | `ChargingDisabled` | fail-safe disable + verify |
| Disabled | `Unmanaged` | **no hardware write** |
| Offline | `Unmanaged` | **no hardware write** |

`Fault` dan `Unmanaged` sengaja berbeda. Fault adalah protective action; Unmanaged berarti daemon relinquish control.

## 7. Transaction hardware yang diharapkan

```text
Decision
  ↓
HardwareTarget
  ↓
if target == Unmanaged:
    update logical state only
else:
    acquire/confirm ownership
    persist operation evidence
    read original/actual state
    write required nodes
    detect partial failure
    read actual state
    verify
    commit ownership state
```

Setiap failure harus menghasilkan state yang dapat dijelaskan, bukan sekadar boolean.

## 8. Startup recovery

Urutan startup harus:

```text
process start
 → acquire singleton lock
 → validate directories/permissions
 → load config
 → load ownership journal
 → recover unfinished operation
 → establish safe controller state
 → initialize reader/netlink/scheduler
 → first fresh snapshot
 → policy evaluation
```

**Policy tidak boleh melakukan mutation sebelum ownership recovery selesai.**

## 9. Concurrency rules

- Hanya satu hardware writer.
- IPC tidak boleh memanggil hardware API langsung.
- Netlink callback tidak boleh menjalankan long-running mutation.
- Scheduler evaluation harus serialized.
- Shutdown harus memenangkan event queue untuk mutation baru.
- Reload config tidak boleh menghasilkan dua effective config yang dipakai bersamaan oleh satu evaluation.

## 10. Android-specific requirements

Vendor dapat memiliki lebih dari satu charging control node dan aktor lain dapat menulis node yang sama. Karena itu userspace ownership adalah **logical lease**, bukan file lock pada sysfs.

Daemon juga harus menganggap `service.sh`/Magisk lifecycle tidak selalu ideal: process dapat dibunuh, boot dapat lambat, node dapat muncul terlambat, dan permission/SELinux dapat berbeda antar perangkat.

## 11. Testing gate

Minimal harus ada:

```text
[ ] deterministic policy tests
[ ] thermal_cutoff=false tests
[ ] Unknown vs Offline tests
[ ] fault recovery N consecutive reads
[ ] hardware partial-write tests
[ ] readback lag tests
[ ] ownership crash-point tests
[ ] corrupt ownership tests
[ ] corrupt config tests
[ ] IPC authorization tests
[ ] IPC flood/bounded-request tests
[ ] graceful shutdown tests
[ ] suspend/resume tests
[ ] external hardware mutation tests
[ ] Android/vendor matrix tests
```

Fault injection wajib mencakup crash pada setiap boundary persistence/write/verify.

## 12. Acceptance criteria

Repository boleh disebut production-ready hanya jika:

1. Tidak ada hardware mutation di luar controller.
2. `Unmanaged` benar-benar tidak menulis charging backend.
3. Fault selalu memiliki deterministic fail-safe behaviour.
4. Shutdown mempunyai satu graceful path.
5. Config invalid tidak menjadi default.
6. Partial write direkonsiliasi.
7. Ownership crash recovery deterministic.
8. Desired/Applied/Actual/Verified dapat diobservasi.
9. IPC privileged commands terproteksi.
10. Compatibility claim memiliki evidence perangkat nyata.

## 13. Definition of Done

```text
[ ] P0 seluruhnya closed
[ ] P1 seluruhnya closed atau memiliki justified exception
[ ] invariants memiliki enforcement point
[ ] setiap invariant punya test
[ ] crash injection pass
[ ] real-device evidence tersedia
[ ] logs dapat menjelaskan setiap hardware operation
[ ] release gate CI aktif
```

```text
Requirement

```
