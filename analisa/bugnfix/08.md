# 08 — Configuration & CLI

## 1. Config lifecycle

Configuration harus melalui satu pipeline yang identik untuk startup, CLI validation, dan reload:

```text
bytes
 ↓
parse TOML
 ↓
schema/version check
 ↓
semantic validation
 ↓
normalize effective values
 ↓
immutable EffectiveConfig
 ↓
runtime
```

Jangan biarkan setiap caller mempunyai aturan validasi sendiri.

## 2. Missing vs invalid

Semantics harus eksplisit:

```text
missing → default/create jika memang policy produk mengizinkan
permission denied → error
I/O failure → error
malformed TOML → error
unknown field/version → reject atau explicit migration
semantic invalid → reject
```

`unwrap_or_default()` pada loader safety-critical tidak boleh digunakan untuk menutupi corruption.

## 3. Validation

Minimal validasi:

```text
0 <= charge_limit <= 100
0 <= resume_limit <= 100
resume_limit < charge_limit
thermal hysteresis > 0
thermal thresholds tidak overflow
interval > 0
retry/backoff bounded
paths berada di lokasi yang diizinkan
```

Validasi harus mencegah konfigurasi yang secara sintaks valid tetapi secara policy mustahil.

## 4. Normalize

`normalize()` menghasilkan effective configuration yang tidak berubah selama satu evaluation:

```rust
let effective = config.clone().normalize()?;
let decision = engine.evaluate(&effective, snapshot);
```

Clamp hanya boleh dilakukan jika memang semantics produk menyatakan clamp. Jangan menggunakan clamp untuk menyembunyikan config error.

## 5. Corrupt config

Anti-pattern:

```text
parse fail
 → default config
 → save default
```

Flow benar:

```text
parse fail
 → retain original bytes
 → log structured error
 → refuse reload/start
 → existing valid runtime config remains active during reload
```

Pada startup tanpa config valid, daemon sebaiknya fail closed sesuai deployment contract daripada diam-diam mengubah behaviour.

## 6. Atomic write

```text
serialize new config
 → validate serialized result
 → temp file same directory
 → write_all
 → fsync
 → rename
 → fsync directory
```

Permission/mode harus dipertahankan. Cleanup temp file dilakukan bila failure.

## 7. Reload transaction

```text
current EffectiveConfig
        │
request reload
        ↓
read new file
        ↓
parse + validate + normalize
        ├─ fail → keep current config
        └─ success → swap atomically
                         ↓
                  reconciliation
```

Jangan mengganti field satu per satu karena policy dapat melihat hybrid configuration.

## 8. Policy impact classification

Perubahan config sebaiknya diklasifikasikan:

```text
policy-relevant → immediate evaluation/reconciliation
hardware profile → capability reprobe + reconciliation
logging-only → no charging mutation
```

Reload tidak boleh otomatis melakukan hardware write dari config loader. Runtime yang mengorkestrasi.

## 9. CLI boundary

CLI adalah API client:

```text
charger-ctl
 → Unix socket
 → request
 → runtime
 → controller
```

Jangan menduplikasi controller logic di CLI.

## 10. Exit codes

Contoh kontrak stabil:

```text
0 success/verified
1 general/runtime error
2 invalid arguments
3 unauthorized
4 unavailable/busy
5 hardware operation failed
6 verification failed
7 timeout
8 config invalid
```

Bedakan command accepted/queued dari operation verified.

## 11. Security

CLI arguments tidak boleh menerima arbitrary sysfs path/value. Jika ada profile selection, hanya identifier yang tervalidasi yang boleh dipilih.

## 12. Testing

```text
[ ] missing config
[ ] malformed TOML
[ ] invalid range
[ ] resume >= limit
[ ] thermal disabled
[ ] unknown schema
[ ] atomic write crash
[ ] reload valid
[ ] reload invalid retains old config
[ ] concurrent reload requests
[ ] CLI timeout
[ ] CLI unauthorized
[ ] CLI does not write hardware directly
```

## 13. Acceptance criteria

1. Satu validation pipeline.
2. Corrupt config tidak pernah ditimpa.
3. Reload atomic.
4. Effective config immutable per evaluation.
5. CLI hanya client.
6. Exit codes terdokumentasi dan stabil.
7. Config mutation tidak melewati controller.
