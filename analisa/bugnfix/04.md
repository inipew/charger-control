# 04 — Hardware Control & Verification

## 1. Scope

`HardwareController` adalah safety boundary antara policy userspace dan charging control kernel. Fokus dokumen ini adalah memastikan setiap mutation memiliki ownership, transaction identity, readback, verification, retry semantics, dan recovery yang benar.

## 2. Kontrak utama

```text
Decision
  ↓
HardwareTarget
  ↓
HardwareController
  ├─ ownership
  ├─ persistence
  ├─ HardwareIo writes
  ├─ readback
  ├─ verification
  └─ recovery
```

Tidak boleh ada:

```text
Policy → sysfs
IPC → sysfs
CLI → sysfs
Monitor → set_charging()
```

## 3. Target semantics

Current target model:

```rust
enum HardwareTarget {
    ChargingEnabled,
    ChargingDisabled,
    Unmanaged,
}
```

Semantics:

- `ChargingEnabled`: daemon memiliki intent untuk charging enabled.
- `ChargingDisabled`: daemon memiliki intent protective/limit untuk charging disabled.
- `Unmanaged`: daemon melepaskan kontrol dan **tidak boleh menulis charging backend**.

Jangan mengimplementasikan `Unmanaged` sebagai `set_charging(true)` atau restore arbitrary default.

## 4. Operation lifecycle

Target flow:

```text
New intent
  ↓
compare desired vs verified/actual
  ↓
if Unmanaged → release logical ownership, no write
  ↓
prepare operation_id
  ↓
persist ownership/operation evidence
  ↓
read baseline actual state
  ↓
apply required nodes
  ↓
collect per-node result
  ↓
read all actual state
  ↓
verify acceptance criteria
  ↓
commit success OR enter recovery
```

`set_charging()` returning success hanya berarti interface menerima write. Jangan langsung mengubah state menjadi `Synced`.

## 5. Ownership before mutation

Sebelum mutation:

```text
ownership = Prepared
operation_id = X
persist durable evidence
```

Baru setelah itu node ditulis. Jika process crash setelah node write, startup dapat mengetahui bahwa daemon pernah memiliki operation aktif.

## 6. Multi-node / partial failure

Android vendor dapat mempunyai beberapa charging control node. Misalnya:

```text
node A → success
node B → EIO
node C → success
```

Controller harus **tidak** menghasilkan `Synced`.

Langkah recovery:

```text
partial result
   ↓
read A/B/C
   ↓
classify actual state
   ├─ target already satisfied → verify/commit
   ├─ all known safe → retry transient failure
   ├─ mixed → converge deliberately
   └─ unknown → protective/fault path
```

Jika target protective `ChargingDisabled`, safe convergence dapat mencoba disable pada node yang diketahui masih aktif, tetapi tetap dibatasi oleh capability profile.

## 7. Node metadata

Setiap control node idealnya mempunyai metadata:

```text
path
operation kind
required / optional
priority
authoritative / supporting
write value
read semantics
retryable errors
verification role
```

Contoh:

```rust
struct ControlNode {
    path: PathBuf,
    required: bool,
    authoritative: bool,
    priority: u8,
    enable_value: String,
    disable_value: String,
}
```

Jangan menganggap semua device memakai nilai `1/0` atau `true/false`.

## 8. Verification model

Pisahkan tiga evidence:

```text
Control state
  = apa yang node control laporkan

Electrical state
  = current/charge behaviour

Sensor state
  = capacity/temp/online/status
```

Untuk `ChargingEnabled`, status charging yang valid dan charger online dapat menjadi primary evidence. Untuk `ChargingDisabled`, control state lebih kuat daripada asumsi `current_ma <= 100`.

Current threshold 100mA dapat menjadi profile-specific secondary evidence, bukan universal law.

## 9. Verification timing

Current verification delays `[500ms, 1s, 2s]` masuk akal sebagai bounded eventual-consistency window, tetapi Android kernel/vendor dapat lebih lambat.

Flow:

```text
write
 ↓ 500ms read
fail
 ↓ 1s read
fail
 ↓ 2s read
fail
 ↓ verification failed
```

Failure tidak otomatis berarti hardware permanently broken. Controller harus membedakan transient lag dan repeated failure.

Jika tiga read gagal berulang kali, gunakan bounded retry backoff seperti:

```text
30s → 60s → 120s → 300s
```

Counter hanya di-reset setelah target benar-benar verified.

## 10. `Mixed` dan `Unknown`

Jangan collapse:

```text
No node
Mixed node state
Unreadable node
Invalid value
```

menjadi satu error. Recovery strategy berbeda.

Contoh:

```text
NoChargingNodeFound
    → capability/profile issue

ChargingStateUnknown
    → cannot prove state

ChargingStateMixed
    → reconciliation required
```

## 11. External mutation

Setelah target verified, vendor HAL/kernel/other root process masih dapat mengubah state.

Jika:

```text
desired = OFF
verified = OFF
later actual = ON
```

maka ini adalah `ExternalModification`, bukan sekadar stale cache.

Controller harus:

```text
read actual
 → classify external mutation
 → bounded reapply
 → verify
```

Jika actor terus melawan, jangan infinite write loop. Naikkan degraded/fault evidence dan beri observability.

## 12. Retry semantics

Retry hanya untuk transient error:

```text
EAGAIN / temporary node absence / known vendor delay
```

Tidak retry tanpa batas untuk:

```text
permission denied
invalid value
unsupported node
corrupt profile
```

Backoff harus bounded dan memakai monotonic clock.

## 13. Generation / operation identity

Jangan menggunakan satu `generation` untuk semua konsep. Pisahkan:

```text
intent_generation
operation_id
ownership_generation
verification_generation
```

Contoh race:

```text
intent #10 = OFF
operation #A starts
intent #11 = ON
operation #B starts
late result #A
```

Late result #A tidak boleh mengalahkan intent #11.

## 14. `force_apply`

`force_apply` boleh digunakan untuk memaksa controller mengevaluasi target setelah transition, tetapi tidak boleh mengubah semantic target.

Khusus:

```text
ChargingDisabled
 → Unmanaged
 → force_apply = true
```

`apply_target(Unmanaged)` tetap wajib tidak melakukan write. Force apply adalah control-flow hint, bukan bypass safety contract.

## 15. Shutdown

Shutdown harus konsisten dengan ownership policy. Jangan melakukan direct:

```rust
control::set_charging(true)
```

dari IPC/worker sebagai shortcut. Runtime harus menentukan apakah shutdown berarti restore previous state atau relinquish ownership. Apa pun pilihannya, proses harus melalui controller agar state dapat dipersist dan diverifikasi.

Jika produk mendefinisikan shutdown sebagai `Unmanaged`, maka final path tidak melakukan charging write.

## 16. Failure matrix

| Failure | Action |
|---|---|
| write rejected before mutation | keep evidence, classify retryable/permanent |
| partial write | readback + reconcile |
| readback unknown | no false success; fault/degraded |
| verify timeout | bounded retry/backoff |
| external mutation | reconcile |
| ownership journal corrupt | recovery/error; never assume clean |
| target Unmanaged | no hardware write |

## 17. Testing

Mock HardwareIo harus dapat menginjeksikan:

```text
[ ] all writes success
[ ] first node fails
[ ] middle node fails
[ ] last node fails
[ ] readback stale
[ ] readback mixed
[ ] readback unknown
[ ] verification delayed
[ ] permanent failure
[ ] external mutation
[ ] crash after persistence
[ ] crash after first write
[ ] crash after all writes
[ ] crash before verification
[ ] retry backoff
```

Test harus memeriksa bukan hanya return value tetapi sequence write/read dan final persisted state.

## 18. Acceptance criteria

1. Semua charging mutation lewat controller.
2. `Unmanaged` tidak pernah memanggil write backend.
3. Apply success tidak dianggap verified success.
4. Partial failure selalu diikuti readback/reconciliation.
5. Unknown dan mixed state dibedakan.
6. Retry bounded dan hanya untuk transient failure.
7. External mutation dapat dideteksi.
8. Late operation result tidak mengalahkan intent terbaru.
9. Shutdown tidak memiliki direct hardware shortcut.
10. Semua operation dapat ditelusuri dengan operation ID.
