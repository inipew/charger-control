# 28 — Release Engineering

## Tujuan
Mencegah build yang compile tetapi tidak aman untuk device nyata.

## Invariant
- **I-REL-001**: release artifact reproducible dan teridentifikasi.
- **I-REL-002**: binary hanya dirilis jika seluruh release gate lulus.
- **I-REL-003**: upgrade dan rollback memiliki prosedur recovery.
- **I-REL-004**: compatibility claims harus didukung evidence.

## Pipeline
```text
format -> lint -> unit tests -> integration tests
 -> fault injection -> security checks
 -> cross compile -> artifact inspection
 -> device matrix -> release candidate -> publish
```

## Artifact metadata
Simpan version, git commit, target architecture, build profile, dan checksum. Binary production harus dapat dikaitkan ke source commit yang tepat.

## Upgrade
Upgrade harus mempertahankan ownership/config yang kompatibel. Jika schema berubah, migration harus atomic dan reversible bila memungkinkan.

Urutan aman:
```text
validate new artifact
 -> stop/restart old daemon safely
 -> recover state
 -> start new daemon
 -> reconcile + verify
 -> mark upgrade successful
```

Jika startup/reconciliation gagal, rollback harus tetap meninggalkan hardware pada safe state.

## Release gate
Release ditolak bila:
- shutdown belum graceful;
- config error masih fallback silently;
- IPC masih unauthorized;
- hardware write bypass controller;
- ownership recovery tidak deterministic;
- compatibility evidence tidak ada;
- fault injection gagal;
- panic/unwrap pada runtime path safety-critical.

## Acceptance criteria
1. Artifact dapat direproduksi atau perbedaan build terdokumentasi.
2. Upgrade/rollback diuji dengan crash injection.
3. Checksum dan version tercatat.
4. Release notes menyatakan device/profile compatibility secara eksplisit.
