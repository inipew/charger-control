# 03 — Policy & State Machine

## 1. Tujuan

`DecisionEngine` adalah pusat keputusan charging. Ia harus pure, deterministik, dapat dites tanpa Android, dan tidak boleh mencampurkan policy state dengan hardware ownership state.

Input canonical:

```text
EffectiveConfig
SensorSnapshot
PreviousPolicyState
CurrentMode / manual intent
```

Output canonical:

```text
ChargePolicyState
HardwareIntent/HardwareTarget
DecisionReason
```

## 2. Pisahkan tiga state

Jangan menggunakan satu enum untuk semua hal.

```text
Policy state:
  Disabled / Offline / Charging / LimitReached /
  ThermalCutoff / Fault / ManualBypass

Hardware state:
  Desired / Applying / Applied / Verified / Failed / Unmanaged

Physical evidence:
  online / status / current / capacity / temperature
```

Contoh: policy `Offline` dapat menghasilkan hardware `Unmanaged`, sementara physical hardware tetap memiliki state terakhirnya.

## 3. Precedence

Urutan harus eksplisit dan didokumentasikan. Recommended:

```text
Shutdown / lifecycle gate
        ↓
Manual safety/recovery gate
        ↓
Daemon Disabled
        ↓
Sensor/Hardware Fault
        ↓
Offline (online == false)
        ↓
Thermal Protection
        ↓
Manual Bypass (jika diizinkan)
        ↓
Charge Limit
        ↓
Normal Charging
```

Kernel/vendor protection berada di luar policy userspace dan tetap dapat memutus charging kapan saja.

## 4. Disabled

Jika:

```toml
enabled = false
```

policy menjadi `Disabled` dan mapping-nya:

```text
Disabled → HardwareTarget::Unmanaged
```

Ini penting. Disabled berarti daemon **tidak memiliki hak untuk mengontrol charging**, bukan berarti daemon memerintahkan charging ON.

Tidak boleh:

```text
Disabled → set_charging(true)
```

## 5. Offline dan Unknown

Semantik wajib:

```text
online == Some(false) → Offline
online == Some(true)  → eligible
online == None        → Unknown
```

`Offline` → `Unmanaged` jika desain daemon memang relinquish control ketika charger dicabut.

`Unknown` tidak boleh otomatis menjadi `Offline`, karena `None` dapat berarti sensor belum tersedia atau read gagal.

Jika evidence required untuk safety tidak tersedia, gunakan `Fault` sesuai classification sensor, bukan memalsukan presence.

## 6. Thermal policy

Bug yang harus ditutup: `max_temp_dc` tidak boleh mengaktifkan thermal logic jika:

```toml
thermal_cutoff = false
```

Jika enabled:

```text
trip:
  temp >= max_temp_dc
      → ThermalCutoff

resume:
  temp <= max_temp_dc - effective_hysteresis
      → kembali ke normal policy
```

Gunakan hysteresis yang telah divalidasi. Jangan menghitung hysteresis dengan overflow/signed ambiguity.

Jika temperature `None`, jangan membuat temperature seolah-olah aman. Classification-nya mengikuti sensor requirement: untuk safety-critical thermal control, missing/invalid temperature dapat menjadi `Fault`.

## 7. Charge limit

Canonical transition:

```text
Charging
  capacity >= charge_limit
      ↓
LimitReached
```

Untuk resume:

```text
LimitReached
  capacity <= resume_limit
      ↓
Charging
```

Jangan menggunakan satu threshold untuk dua arah karena noise menyebabkan:

```text
79 → 80 → 79 → 80 → ...
```

Pastikan validation menjamin hubungan yang masuk akal antara `resume_limit` dan `charge_limit`.

## 8. Fault state dan recovery

Fault harus memiliki entry reason dan recovery streak.

Pattern yang benar:

```text
Normal
  ↓ invalid required evidence
Fault
  ↓ valid snapshot #1
Fault(recovery=1)
  ↓ valid snapshot #2
Fault(recovery=2)
  ↓ valid snapshot #N
Re-evaluate
```

Jangan reset counter secara tidak sengaja sebelum branch Fault dievaluasi. Invalid evidence selama Fault harus mengembalikan streak ke zero.

Contoh struktur:

```rust
if self.policy == ChargePolicyState::Fault {
    if snapshot_is_valid(snapshot) {
        self.fault_recovery_reads += 1;
        if self.fault_recovery_reads >= FAULT_RECOVERY_READS {
            self.fault_recovery_reads = 0;
            return self.evaluate_normal(snapshot, cfg);
        }
        return fault_decision("waiting for consecutive recovery reads");
    }

    self.fault_recovery_reads = 0;
    return fault_decision("required sensor still invalid");
}
```

## 9. Policy → target mapping

```rust
fn policy_to_target(policy: ChargePolicyState) -> HardwareTarget {
    match policy {
        ChargePolicyState::Disabled
        | ChargePolicyState::Offline => HardwareTarget::Unmanaged,

        ChargePolicyState::Charging => HardwareTarget::ChargingEnabled,

        ChargePolicyState::LimitReached
        | ChargePolicyState::ThermalCutoff
        | ChargePolicyState::Fault => HardwareTarget::ChargingDisabled,

        ChargePolicyState::ManualBypass => HardwareTarget::Unmanaged,
    }
}
```

Manual bypass sebaiknya menjadi explicit intent/mode dan tetap melalui controller; jangan biarkan mapping ini membuka direct hardware path.

## 10. Transition examples

### Normal → Limit

```text
online=true
capacity=80
limit=80
        ↓
LimitReached
        ↓
ChargingDisabled
        ↓
controller disables hardware
        ↓
readback + verify
```

### Limit → Resume

```text
capacity=79
resume=75
        ↓
remain LimitReached
```

Baru ketika `capacity <= 75`:

```text
Charging
 → ChargingEnabled
```

### Thermal

```text
temp=450, max=450
 → ThermalCutoff
 → ChargingDisabled
```

Pada 449 tidak otomatis resume jika hysteresis membutuhkan 440.

### Offline

```text
online=false
 → Offline
 → Unmanaged
 → no charging write
```

Saat reconnect, policy dihitung ulang dari fresh snapshot; jangan mengandalkan state lama saja.

## 11. Determinism requirements

DecisionEngine tidak boleh:

- membaca sysfs;
- memanggil `Instant::now()` untuk menentukan policy;
- mengakses config file;
- mengirim command IPC;
- menulis state persistence;
- melakukan sleep/retry.

Semua itu milik orchestrator/controller.

## 12. Failure semantics

Jika decision engine menerima input yang secara internal tidak mungkin terjadi, lebih baik mengembalikan typed error/fault daripada memilih `ChargingEnabled` sebagai default.

Safety rule:

```text
Ambiguous safety evidence
      ↓
Do not assume safe charging
      ↓
Fault / protective target
```

Tetapi jangan menyamakan `online=None` dengan `online=false`.

## 13. Testing

Wajib menguji:

```text
[ ] disabled → unmanaged, no write
[ ] offline → unmanaged, no write
[ ] online unknown semantics
[ ] thermal disabled ignores temperature cutoff
[ ] thermal enabled trip boundary
[ ] thermal hysteresis boundary
[ ] charge limit exact boundary
[ ] resume exact boundary
[ ] fault entry
[ ] invalid snapshot resets recovery streak
[ ] N consecutive valid reads recover
[ ] one invalid read after partial recovery resets streak
[ ] identical input is deterministic
[ ] priority ordering
[ ] Fault → disabled target
```

Property test yang bagus: untuk konfigurasi valid dan snapshot sama, hasil decision tidak berubah akibat urutan pemanggilan test sebelumnya.

## 14. Acceptance criteria

Policy dianggap benar bila setiap state mempunyai:

1. entry condition;
2. exit condition;
3. precedence;
4. target mapping;
5. reason code;
6. failure semantics;
7. recovery rule;
8. automated test.

Tidak boleh ada transition implisit yang hanya terjadi karena branch ordering kebetulan.
