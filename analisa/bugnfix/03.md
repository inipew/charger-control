# 03 — POLICY & STATE MACHINE SPECIFICATION

## Tujuan

Memisahkan fakta sensor, keputusan policy, actual hardware, dan ownership sehingga tidak ada state yang ambigu.

## State utama

```rust
enum ChargerPresence { Online, Offline, Unknown }

enum ChargeState {
    Disabled,
    Offline,
    Charging,
    LimitReached,
    ThermalCutoff,
    ManualBypass,
    Fault,
}

enum ElectricalState { Charging, Discharging, Idle, Unknown }
```

## Input policy

Policy menerima `SensorSnapshot`, `Config`, actual hardware/sync state, dan current policy state.

Policy **tidak** boleh membaca sysfs atau menulis hardware.

## Priority

```text
Shutdown
> Recovery
> Disabled
> Hardware fault
> Sensor fault
> Offline
> Thermal protection
> Manual bypass
> Charge limit
> Normal charging
```

Priority harus diwujudkan dalam satu tempat, bukan tersebar di monitor/controller.

## Charge limit

```text
Charging && capacity >= charge_limit
    → LimitReached

LimitReached && capacity <= resume_limit
    → Charging
```

Boundary `==` wajib diuji.

Invariant:

```text
0 < resume_limit < charge_limit <= 100
```

## Thermal

Jika feature disabled, tidak ada thermal transition.

Jika enabled:

```text
T >= cutoff
    → ThermalCutoff

ThermalCutoff && T <= cutoff - hysteresis
    → Charging / LimitReached
```

Hysteresis tidak boleh hard-coded.

## Offline

```text
Online → Offline
```

harus terjadi dari authoritative presence observation, bukan hanya karena `current=0`.

Saat offline, policy tidak boleh menganggap hardware sedang charging. Scheduler menggunakan fakta `online` dan `charging` yang terpisah.

## Unknown

Jika sensor penting tidak tersedia:

```text
valid → normal policy
invalid/unknown → degraded/fault
```

Tidak boleh:

```text
read failure → 0
0 → charging enabled
```

## Fault recovery

Fault tidak langsung pulih karena satu sample bagus. Gunakan sejumlah consecutive valid reads, misalnya 3.

```text
Fault
 ↓ valid #1
Fault
 ↓ valid #2
Fault
 ↓ valid #3
Normal evaluation
```

Jumlah recovery reads harus configurable/constant dan diuji.

## Config change

Config reload harus memicu:

```text
ConfigChanged
→ validate
→ replace runtime config
→ invalidate stale prediction
→ evaluate immediately
→ reconcile hardware
```

Contoh wajib: limit 80 → 90 saat battery 80% harus dievaluasi berdasarkan config baru, bukan mempertahankan state lama secara membabi buta.

## Decision result

Gunakan hasil yang menjelaskan alasan:

```rust
struct PolicyDecision {
    state: ChargeState,
    intent: HardwareIntent,
    reason: DecisionReason,
    generation: u64,
}
```

`DecisionReason` harus dapat menjelaskan mengapa charging enabled/disabled.

## Transition tests

Minimal test matrix:

| Current | Input | Expected |
|---|---|---|
| Charging | capacity == limit | LimitReached |
| LimitReached | capacity == resume | Charging |
| Charging | temp == cutoff | ThermalCutoff |
| ThermalCutoff | temp == cutoff-hysteresis | Normal policy |
| Charging | offline | Offline |
| Offline | online | Normal policy |
| Any normal | critical sensor unknown | Fault/degraded |
| Fault | consecutive valid reads | recovery |

## Rule

Policy adalah pure decision layer. Jika sebuah policy test membutuhkan `/sys`, boundary arsitektur sudah salah.
