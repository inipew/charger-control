# 02 — Architecture Invariants

## 1. Tujuan

Dokumen ini mendefinisikan invariant yang harus selalu benar pada runtime `charger-control`. Invariant bukan saran style: pelanggaran invariant adalah bug walaupun happy-path test lulus.

Arsitektur yang dituju:

```text
Kernel/power_supply
        ↓
Reader → Snapshot
        ↓
Policy ← Config
        ↓
HardwareIntent
        ↓
HardwareController
   ┌────┴────┐
Ownership  Verification
   └────┬────┘
        ↓
HardwareIo → sysfs
```

## 2. Boundary ownership

| Boundary | Boleh | Tidak boleh |
|---|---|---|
| Reader | read/parse/normalize | write hardware |
| Snapshot | represent evidence | perform I/O |
| Policy | decide target | sysfs/IPC/filesystem |
| Scheduler | decide WHEN | decide charging policy |
| Netlink | wake/reconnect | hardware mutation |
| Controller | orchestrate mutation | menerima arbitrary path |
| HardwareIo | low-level I/O | policy decision |
| Ownership | durable control evidence | policy decision |
| IPC | request/event | direct sysfs |

## 3. Policy invariants

### I-POL-001 — Deterministic decision

Input yang sama:

```text
EffectiveConfig + SensorSnapshot + previous policy + mode
```

harus menghasilkan output yang sama. Jangan membaca sysfs, wall clock, filesystem, random, atau global mutable state dari `DecisionEngine`.

### I-POL-002 — No I/O

Policy tidak boleh memperbaiki sensor, menulis config, menulis hardware, atau mengirim IPC. Semua side effect dilakukan layer luar.

### I-POL-003 — Thermal master switch

`thermal_cutoff=false` membuat seluruh userspace thermal transition/prediction non-authoritative. `max_temp_dc` tidak boleh mengaktifkan thermal policy sendiri.

### I-POL-004 — Hysteresis

Boundary resume harus berbeda dari boundary trip. Untuk limit:

```text
capacity >= charge_limit → disable
capacity <= resume_limit  → resume
```

Untuk thermal:

```text
temp >= max_temp → cutoff
temp <= max_temp - hysteresis → resume
```

### I-POL-005 — Unknown semantics

```text
online=false → Offline
online=true  → eligible
online=None  → Unknown
```

`None` tidak boleh otomatis dianggap unplugged.

### I-POL-006 — Fault recovery requires consecutive evidence

Sensor invalid mereset recovery streak. Recovery membutuhkan N snapshot valid berturut-turut, bukan satu read sukses yang kebetulan benar.

## 4. Hardware invariants

### I-HW-001 — Single writer

Satu-satunya layer yang boleh melakukan charging mutation adalah `HardwareController` melalui `HardwareIo`.

### I-HW-002 — Apply != verify

```text
write() == accepted by interface
readback == actual
verify == actual satisfies target
```

Ketiganya berbeda.

### I-HW-003 — Partial write reconciliation

Jika sebagian node berhasil dan sebagian gagal, controller wajib membaca actual state. Jangan menganggap state tetap sama seperti sebelum operasi.

### I-HW-004 — Capability-aware nodes

Required, optional, authoritative, fallback, dan unavailable node harus dibedakan. "Node tidak ada" bukan otomatis error fatal jika profile memang tidak membutuhkan node tersebut.

### I-HW-005 — Domain normalization

Konversi unit, sign, range, dan raw integer dilakukan sebelum nilai masuk policy.

### I-HW-006 — Unmanaged means no write

`HardwareTarget::Unmanaged` hanya mengubah logical ownership/state. Controller tidak boleh memanggil `set_charging()`.

## 5. Ownership invariants

### I-OWN-001 — Evidence before mutation

Sebelum operation yang membutuhkan ownership, durable evidence harus sudah tersimpan.

### I-OWN-002 — Commit after verification

Ownership release/operation commit tidak boleh menyatakan sukses sebelum restore/target verified.

### I-OWN-003 — Crash evidence survives

Crash setelah write tetapi sebelum clear harus tetap meninggalkan evidence agar startup recovery dapat mengetahui operation terakhir.

### I-OWN-004 — Corruption is not valid state

Corrupt/truncated/unknown-version ownership file masuk recovery/error path, bukan dianggap `Unmanaged` atau default.

## 6. Runtime invariants

### I-RUN-001 — One orchestrator

Runtime/monitor adalah satu-satunya komponen yang mengurutkan snapshot → policy → hardware.

### I-RUN-002 — Serialized evaluation

Dua evaluation tidak boleh mengubah hardware secara bersamaan.

### I-RUN-003 — Shutdown dominance

Setelah shutdown mulai, evaluation baru yang dapat menyebabkan mutation harus ditolak atau dibatalkan.

## 7. IPC invariants

### I-IPC-001 — Commands are intents

IPC menghasilkan command/event. Runtime yang menentukan bagaimana command dieksekusi.

### I-IPC-002 — Authorization

Socket Unix permission, group, command authorization, dan bounded request harus diterapkan sebelum command diproses.

### I-IPC-003 — Graceful shutdown

IPC tidak boleh `process::exit()` dari worker. Ia hanya mengirim `ShutdownRequested`.

### I-IPC-004 — Bounded resources

Request length, number of arguments, response size, processing time, dan concurrent clients harus dibatasi.

## 8. Temporal invariants

### I-TIME-001 — Monotonic deadlines

Backoff, retry, debounce, timeout, deadline, dan snapshot age memakai `Instant`/monotonic source.

### I-TIME-002 — Event freshness

Event lama tidak boleh menimpa state baru. Jika dibutuhkan, gunakan sequence/generation.

### I-TIME-003 — Operation identity

Setiap hardware operation mempunyai correlation/request/operation ID yang dapat dilacak dari decision sampai verification.

## 9. Configuration invariants

### I-CFG-001 — One validation path

CLI, daemon startup, dan reload menggunakan validator/domain normalization yang sama.

### I-CFG-002 — No silent fallback on invalid

Parse/I/O/validation error tidak boleh berubah menjadi default.

### I-CFG-003 — Atomic persistence

Config ditulis temp file → flush/fsync → rename → optional directory fsync. File asli tidak disentuh sampai new file valid.

### I-CFG-004 — Transactional reload

Evaluation memakai satu immutable `EffectiveConfig` snapshot. Reload baru berlaku sebagai unit lengkap, bukan field-per-field.

## 10. Scheduler invariants

### I-SCH-001 — Scheduler only chooses WHEN

Scheduler tidak boleh membuat keputusan charging ON/OFF.

### I-SCH-002 — Netlink accelerator

Jika netlink mati, correctness tetap dijaga oleh polling/heartbeat.

### I-SCH-003 — Debounce/coalescing

Event storm tidak menghasilkan unbounded evaluations.

### I-SCH-004 — Prediction is advisory

EMA/ETA boleh mengoptimalkan wakeup, tetapi tidak boleh menjadi safety proof yang mengalahkan actual sensor threshold.

## 11. Error invariants

Bedakan minimal:

```text
Unknown sensor
Offline charger
Hardware unavailable
Hardware operation failed
Verification failed
Policy Fault
```

Jangan collapse semuanya menjadi satu boolean.

## 12. Enforcement matrix

| Invariant | Enforcement | Test |
|---|---|---|
| I-HW-001 | module visibility/API | compile + mutation audit |
| I-HW-002 | controller verify state | mock readback |
| I-HW-003 | reconciliation | partial-write injection |
| I-OWN-003 | journal | crash injection |
| I-IPC-003 | runtime owner | shutdown integration |
| I-CFG-002 | loader | corrupt TOML test |
| I-SCH-002 | heartbeat | netlink disabled test |
| I-TIME-001 | Clock abstraction | fake clock |

## 13. Review rule

Setiap PR yang mengubah charging behaviour wajib menjawab:

```text
Invariant apa yang disentuh?
Boundary mana yang berubah?
Failure mode apa yang baru?
Test apa yang membuktikan behaviour?
Apakah startup/shutdown ikut berubah?
Apakah vendor/external actor dapat mengintervensi?
```

## 14. Definition of Done

Semua invariant di atas harus memiliki enforcement point nyata dan minimal satu automated test. Invariant safety-critical tidak boleh hanya berada di komentar.
